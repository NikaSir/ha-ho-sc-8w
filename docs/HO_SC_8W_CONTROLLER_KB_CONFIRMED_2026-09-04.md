# HO-SC-8W — подтверждённые факты протокола DP38

Дата: 2026-09-04
Статус: каноническое дополнение к `HO_SC_8W_CONTROLLER_KB_RU.md`.
При расхождении с более ранними исследовательскими формулировками этот документ имеет приоритет для перечисленных ниже фактов.

## Уровень A — физически подтверждено на NikaS HO-SC-8W

### 1. Полное автономное чтение программ 1–8

Штатный механизм из APK IIC-800 физически подтверждён на нашем HO-SC-8W.

Инициатор чтения:

```text
DP38 = 0000000000000000000000000000000000000000
```

После одной этой команды контроллер сам последовательно публикует отдельные 20-байтовые ответы DP38 для зон 1…8.

Канонический алгоритм Local:

```text
persistent socket
  -> DP38 = 20 x 00
  -> receive() Z1
  -> receive() Z2
  -> ...
  -> receive() Z8
  -> snapshot 8/8 valid
```

После trigger нельзя вставлять `status()`/`updatedps()` между ответами: нужно дочитать последовательность через persistent `receive()`.

Оператор у физического контроллера не требуется. Старое требование вручную открывать зоны 1–8 относится только к прежнему диагностическому workaround и больше не является штатным способом получения программ.

Полученный натурный снимок 8/8 подтвердил свежие блоки всех зон без действий на приборе.

### 2. READ selector и WRITE selector различаются

READ byte0 содержит обычный номер зоны:

```text
Z1..Z8 = 01 02 03 04 05 06 07 08
```

WRITE byte0 является one-hot маской:

```text
Z1..Z8 = 01 02 04 08 10 20 40 80
```

Формула:

```text
1 << (zone - 1)
```

Исторически запись с `08` как якобы selector зоны 8 фактически затронула зону 4. Поэтому write-side selector никогда нельзя строить из read-side номера зоны.

### 3. Изолированная запись Zone 7 selector 0x40 подтверждена

Исходный READ зоны 7:

```text
0700FFFFFFFFFFFFFFFFFFFFFFFF03011A090311
```

Подготовленный WRITE:

```text
4011FFFFFFFFFFFFFFFFFFFFFFFF03011A090311
```

Ожидаемый READ-back:

```text
0711FFFFFFFFFFFFFFFFFFFFFFFF03011A090311
```

Побайтовый plan diff:

```text
byte 0: 07 -> 40   write-side selector only
byte 1: 00 -> 11   duration 0 -> 17 min
```

После единственной физической записи полный автономный read-back 1–8 вернул:

```text
Z7 actual = 0711FFFFFFFFFFFFFFFFFFFFFFFF03011A090311
```

Он полностью совпал с expected read-back.

Зоны 1–6 и 8 остались byte-for-byte неизменными.

Следовательно, для Zone 7 one-hot selector `0x40` физически подтверждён как изолированный адрес записи.

### 4. Duration byte1 подтверждён записью

Для зоны 7 byte1 физически подтверждён как длительность в минутах:

```text
00 -> 11 hex
0  -> 17 min
```

Изменение не затронуло остальные 18 информационных байт зоны и соседние зоны.

## Канонический transactional DP38 writer

Любая будущая запись программы должна использовать только последовательность:

1. Native fresh refresh 1–8 через `DP38=20x00` + `receive()`.
2. Сохранить exact baseline всех 8 зон.
3. Взять exact READ block целевой зоны.
4. Изменить только проверяемое поле.
5. Только в write-копии заменить byte0 на one-hot selector.
6. Построить expected READ, вернув byte0 к обычному номеру зоны.
7. Показать dry-run diff до dispatch.
8. Непосредственно перед dispatch повторно выполнить native refresh 1–8.
9. При любом stale baseline отменить транзакцию.
10. Отправить ровно один 20-byte DP38 block.
11. Не retry после dispatch.
12. Не делать автоматический rollback.
13. Немедленно выполнить native read-back 1–8.
14. Целевая зона должна точно совпасть с expected READ.
15. Все остальные зоны должны быть byte-for-byte неизменны.

## Production policy

- Полный DP38 snapshot без оператора теперь считается штатным подтверждённым механизмом Local.
- Старый операторский snapshot остаётся только историческим/аварийным диагностическим инструментом.
- Любая DP38 запись обязана сама получать свежий snapshot; persistent cache не является достаточным preflight.
- Разблокировать массовое редактирование production-зон до последовательной проверки остальных полей на свободной зоне 7 нельзя.

## Следующая серия натурных тестов

Проверять по одному полю, каждый раз через полный 1–8 preflight/read-back:

1. start time — один слот;
2. rain sensor follow;
3. program enabled;
4. weekly mask;
5. interval mode + interval days + anchor date;
6. odd/even semantics;
7. после подтверждения — универсальный редактор программы.
